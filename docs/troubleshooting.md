# Troubleshooting

When you do not know where to look, `ot-gateway doctor` in the gateway's folder runs every check in order (the config, the broker, the running gateway, each device, the BACnet/IP port, the disk and the clock) and prints one line each, with the one command to run next; `--json` gives every finding with its `code`, `hint` and `next`. Otherwise start with the status page (`http://127.0.0.1:8080`, see [operations.md](operations.md)) or the retained health topic `site/building/$gateway/<id>/health`: each device is `ok`, `starting` or `failing` with a reason. In a terminal on the gateway, `ot-gateway status` in the gateway's folder says the same, with since when and why a device fails, the first thing to check for it, and since when the broker is away (exit code 1 while something fails); while all is well again it still names the devices that failed and the broker outages of the last 15 minutes, and the active alarms. `ot-gateway events --since 1h` says what broke, when, why (with the first thing to check, and when several devices failed together, that they likely share a cause) and when it came back, alarms raised and cleared too, without polling (`--follow` to watch it change); `ot-gateway history <device>/<point>` shows what a point did meanwhile, and when a switch or an alarm changed; `ot-gateway messages` how many messages went out per topic since start (or `--since 10m`) and reached the broker (see [What changed and when](operations.md#what-changed-and-when)). Both name the gateway first: when `status` says `WRONG GATEWAY`, another gateway answers on the config's status port (two on one machine, or an old SSH tunnel), so its report would be about the wrong building. Then the log: `ot-gateway logs --level warn` prints the gateway's recent warnings and errors from memory, also without access to Docker; the whole log is `docker compose logs gateway --since 10m` in the gateway's folder, or `journalctl -u ot-gateway -f` under systemd: it records a problem once when it starts and once when it ends, so search for the device id. Quoted messages below are what the log says.

## The gateway does not start

| Symptom                                                                       | Cause and fix                                                                                                                                   |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| A `SchemaError` with a path, e.g. `at ["devices"][2]["points"][0]["address"]` | The config. The message names the key and the rule; [configuration.md](configuration.md) has every key. Check with `--check` before restarting. |
| `mqtt.url must not contain credentials`                                       | Move them: `mqtt.username`, and the password in the env file under the name in `mqtt.passwordEnv`.                                              |
| `MQTT_PASSWORD is not set` (the name `mqtt.passwordEnv` gives)                | The variable is unset or empty: put the password in `ot-gateway.env` next to the config, or in `/etc/ot-gateway/gateway.env` under systemd.     |
| `BufferLocked`                                                                | Another gateway has the same `buffer.path` open. Two gateways never share an outbox.                                                            |
| `could not open the BACnet/IP endpoint, trying again`                         | UDP 47808 is taken, usually by another BACnet program on the host (or `--discover` still running). Readings from other devices carry on.        |

## The broker

| Symptom                                                                                                                                     | Cause and fix                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MQTT connect failed, retrying` with `ECONNREFUSED`                                                                                         | Nothing listens at that address: the broker is down, the port is wrong, or it listens on another interface.                                                                                                                                                                                                                                                                      |
| The same, with `ETIMEDOUT` or no answer                                                                                                     | A firewall, or a wrong address. The gateway retries every few seconds, up to 15 s apart; values meanwhile go to the outbox.                                                                                                                                                                                                                                                      |
| `MQTT broker does not speak MQTT 5, connecting with MQTT 3.1.1`                                                                             | Not a fault: an older broker (Mosquitto before 1.6, many PLC and cloud brokers). The gateway goes on with 3.1.1; see `mqtt.version` in the configuration reference for what that leaves out.                                                                                                                                                                                     |
| `MQTT broker refused the connection`                                                                                                        | The reason is in the message: bad user name or password, not authorized, or the broker is busy. Credentials come from `mqtt.username` and the env file.                                                                                                                                                                                                                          |
| Connected, then lost again every few seconds; `session taken over (0x8e)`, or `connection closed … soon after connecting, 3 times in a row` | Another client uses the same client id (two gateways with one config, or `mqtt.clientId` copied). Each connect kicks the other. Give each gateway its own `mqtt.clientId`.                                                                                                                                                                                                       |
| `another gateway, "<id>", is online in site/building with the same device ids` (a warning and a `gateway-conflict` event)                   | Two gateways publish into the same topics, so whoever reads them gets both gateways' values mixed: a copied folder, or a second gateway started on a laptop to test. Stop one, or give one another `site`, `building` or device ids. With the same gateway `id` too, the warning says `another gateway with this gateway's id`: also give each its own `id` and `mqtt.clientId`. |
| `mqtt://localhost` works on the host, not in a container (or the other way round)                                                           | `localhost` is both `127.0.0.1` and `::1`, and a broker may listen on only one. The gateway tries each address for up to 2 s; if it still fails, name the address the broker listens on, e.g. `mqtt://127.0.0.1:1883`.                                                                                                                                                           |
| `mqtts://` fails                                                                                                                            | The broker's certificate must be valid for the host name in the URL and chain to a CA the system trusts.                                                                                                                                                                                                                                                                         |
| `ot-gateway broker`: `round trip: NO ANSWER` (exit code 1, `"ok": false`)                                                                   | The broker took the message but did not deliver it back: its ACL lets this user publish under `site/building/#` but not subscribe there, or the reverse. Allow both; the gateway needs to read its own topics.                                                                                                                                                                   |
| `ot-gateway watch` shows `retained (from gateway <id>)`, `(device not in this config)` or `(point not in this config)`                      | The broker keeps those from another gateway or an older config: a gateway that was replaced, a renamed device. If nothing reads them, clear each with `ot-gateway publish <topic> --retain` (no payload). The gateway clears the `$meta` of its own removed points by itself.                                                                                                    |
| `ot-gateway publish` prints `QoS 0: the broker allows QoS 0 only`                                                                           | The broker's CONNACK caps QoS at 0, so the message went out unacknowledged and the outbox cannot confirm delivery. Raise the broker's maximum QoS if it has one.                                                                                                                                                                                                                 |
| `MQTT broker refused a subscription; nothing published on it will arrive`                                                                   | The broker's ACL does not let the gateway subscribe to the filters the log names: `site/building/+/+/$set` (commands) `site/building/$gateway/+/health` (to notice another gateway publishing into the same topics) or `site/building/<device>/+/$meta` (to clear the metadata of removed points). Values still flow.                                                            |

## Modbus TCP devices

| Symptom                                                                                                     | Cause and fix                                                                                                                                                                                                                                                                                                                                                                               |
| ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `failing`, reason `connection`                                                                              | Wrong IP or port, a firewall, or the device takes one client at a time and the BMS already has it. Many meters and Modbus gateways allow one or two connections.                                                                                                                                                                                                                            |
| `failing`, reason `timeout`                                                                                 | The device takes the connection but does not answer: wrong `unitId` behind a Modbus gateway (each serial device has its own), or a serial bus too slow for the poll interval.                                                                                                                                                                                                               |
| `connection closed by the peer` for a second device on the same gateway, or only one device at a time works | Something else holds the gateway's connection slots (the BMS, a commissioning tool, a second OT Gateway): many accept only one or two connections. Devices on the same `host` and `port` in one OT Gateway config already share one connection.                                                                                                                                             |
| Timeouts now and then, on a Modbus gateway or serial bridge                                                 | Requests arrive back to back faster than the bridge forwards them. Set `requestGapMs` (50–200).                                                                                                                                                                                                                                                                                             |
| A range is refused that reads fine point by point                                                           | The device limits how much one read may ask for: lower `maxRegistersPerRead` (16 or 32 are common limits).                                                                                                                                                                                                                                                                                  |
| `device refused a read`, exception `illegal_data_address`                                                   | The address does not exist: datasheets count from 1 or write 40001 for holding address 0, so try one lower; or the register is in the other table (`input` vs `holding`). The other blocks keep reading.                                                                                                                                                                                    |
| `device refused a read`, exception `gateway_target_failed_to_respond` (11)                                  | A Modbus gateway answers for the device, but nothing behind it answers as this unit id, so every register and table fails alike: set `unitId` to the device's own Modbus address (its display or settings), then check its power, the RS-485 wiring and the gateway's serial settings. `ot-gateway probe <host> <register> --unit-id <n>` tries another unit id without changing the config |
| `device refused a read`, exception `gateway_path_unavailable` (10)                                          | The Modbus gateway has no route for this unit id: set up its serial port for the device, or use the unit id it routes                                                                                                                                                                                                                                                                       |
| Values that are absurd but change                                                                           | The byte order: a float32 that reads `1.4e-41` or `2.6e+20` where `21.5` belongs, or a counter in the billions, means `byteOrder` is wrong. Try `CDAB` first (low word first), then `BADC` and `DCBA`, or let `ot-gateway probe <host> <register>` show all of them at once.                                                                                                                |
| Values off by a factor of 10, 100 or 1000                                                                   | `scaling.factor`: many devices send tenths or hundredths in an integer register.                                                                                                                                                                                                                                                                                                            |
| Values near 65535 that should be small negatives                                                            | `uint16` where the device sends `int16` (and the same for 32-bit).                                                                                                                                                                                                                                                                                                                          |
| `point value is not a finite number, not publishing it`                                                     | A float register holding NaN or infinity, often a sensor that is disconnected or out of range. The point is skipped until it reads a number again.                                                                                                                                                                                                                                          |

## BACnet/IP devices

| Symptom                                                                                                    | Cause and fix                                                                                                                                                                                                                                                                                                                                                                                                          |
| ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `starting` forever, or `device … did not answer Who-Is`                                                    | Who-Is does not reach it: set `bacnet.broadcastAddress` to the subnet's broadcast (`192.168.1.255`), keep `bacnet.bindAddress` at `0.0.0.0`, and on another subnet set `bacnet.bbmdAddress`. Or give the device a fixed `address`.                                                                                                                                                                                     |
| `--discover` finds nothing                                                                                 | The same causes, or the gateway is running and holds UDP 47808: stop it first. With the device's address from a device list, `ot-gateway discover --address ip[:port]` asks it directly, past a missing BBMD or on another port.                                                                                                                                                                                       |
| `demo`: `error: port 1883 (TCP, the test MQTT broker) is in use, probably by ...`                          | The demo listens on TCP 1883, 5020 and 8080 and UDP 47808 and 47809, and checks them before it starts. Stop the program named (another broker, a running gateway, another demo, a test bench), or skip the demo.                                                                                                                                                                                                       |
| `discover`: `the BACnet/IP port 0.0.0.0:47808 is in use by another program`                                | A running gateway, the demo or a BACnet tool holds the port. Stop it and discover again, or set `bacnet.port` in the config to a free port (devices that answer a broadcast on 47808 are then only found with `--address`). `discover --address ip[:port]` needs neither: it asks from a free port when the configured one is taken, and the device answers there.                                                     |
| `the device at … is device 2001, not device 2002`, or `… is not device 2002: it has no device object 2002` | Another BACnet device answers at the device's `address`, so the gateway reads nothing from it rather than publish that device's values under this one. Either `deviceInstance` is wrong (put in the instance the error names, if that is the device you mean) or the address is (another host, or another port when several devices share one). `ot-gateway discover` lists each device with its instance and address. |
| `simulate`: `UDP port 47808 is in use`                                                                     | A gateway with BACnet devices, the demo or another simulator holds the port on this machine. Stop it, or run the device on another port with `simulate bacnet --port 47810` and discover it with `--address ip:47810` ([Try BACnet with two machines](try-bacnet.md)).                                                                                                                                                 |
| `BACnet device stopped answering`                                                                          | The device or the network. Requests are resent `bacnet.retries` times, `bacnet.requestTimeoutMs` apart, before a read counts as failed.                                                                                                                                                                                                                                                                                |
| `cannot read point`, `object: unknown-object`                                                              | The object instance changed (the device was reprogrammed). Run `--discover` again.                                                                                                                                                                                                                                                                                                                                     |
| `device refused a COV subscription, polling the object instead`                                            | Normal for objects or devices without change-of-value support; nothing to do.                                                                                                                                                                                                                                                                                                                                          |
| `ignored a Forwarded-NPDU from an address that is not the configured BBMD`                                 | Messages from another subnet arrive through a BBMD the config does not name. Set `bacnet.bbmdAddress` if it is yours; if it is not, something on the LAN is forging BACnet traffic.                                                                                                                                                                                                                                    |

## Commands

Every command gets a result on `…/$set/result`, unless its device or point level could never be an id (not a slug of at most 64 characters): such a command is only counted as `unknown-point`. `rejected` never reached the device; `failed` was attempted. Rejections for unknown and read-only points are logged when a run of them starts, then as a count at most once a minute; every other command is logged one by one.

`ot-gateway write <device/point> <value>` sends a command and prints its result. When it was not written it exits with 1 and says why; with `--json` the failure has a `code`, a `hint` and `written` (`false` when no device saw it, `"unknown"` when it may have). `unknown-point`, `not-writable`, `wrong-type` and `out-of-range` come from the config it read, before anything was sent, or from the running gateway when that one's config differs. `command-refused` means the broker's access rules did not let the command through; `command-unconfirmed` that the connection broke before the broker confirmed it, so it may have arrived. `no-result` means no gateway answered within `--timeout` (25 s): it is not running, runs another config, or is connected to another broker (`ot-gateway status`). `timeout` means the device did not answer the gateway in time and may have applied it anyway: read the point back before sending it again.

| Result                      | Meaning                                                                                                                                                 |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `rejected retained`         | Published with the retain flag. Commands must be live; clear the retained message (publish an empty retained one).                                      |
| `rejected expired`          | It waited more than 10 s (or its MQTT message expiry) behind other commands to the same device. Usually the device is slow or not answering.            |
| `rejected unknown-point`    | No such device or point in the config.                                                                                                                  |
| `rejected not-writable`     | The point lacks `writable: true`.                                                                                                                       |
| `rejected invalid-payload`  | The payload must be exactly `{"value": …}`, nothing else beside it.                                                                                     |
| `rejected wrong-type`       | `true`/`false` for a binary point, a number otherwise, a whole number from 1 for a multi-state one; `null` only for BACnet.                             |
| `rejected out-of-range`     | Outside the point's `limits`.                                                                                                                           |
| `failed device-unavailable` | The device is not running (failing to connect, or restarting).                                                                                          |
| `failed timeout`            | No answer within 10 s. The device may have applied it: read the point before sending again.                                                             |
| `failed protocol`           | The device refused it (a Modbus exception, a BACnet error such as `write-access-denied`); the message says which.                                       |
| No result at all            | The gateway never got the command: the broker's ACL, a topic typo, or more than 16 waiting for one device (`too many commands waiting, dropping them`). |

## The outbox

| Symptom                                               | Cause and fix                                                                                                                                   |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Rows waiting keeps growing                            | The broker is unreachable or refusing; see above. Rows drain in order once it is back.                                                          |
| `buffer cannot store messages; publishing directly …` | The disk is full or the file is locked. Values go straight to the broker while it takes them; free space and buffering resumes on its own.      |
| `buffer file was unusable, moved it aside …`          | The file was corrupt (an SD card fault, a power cut). A new one started; the old one is kept beside it as `*.corrupt-<time>`.                   |
| `broker rejected buffered messages, dropped them`     | The broker refused stored messages outright (too large, not authorized). Retrying cannot help; they are counted in `ot_gateway_buffer_dropped`. |

## The status page

| Symptom                                                  | Cause and fix                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Not reachable from another machine                       | It listens on `127.0.0.1` by default. Use an SSH tunnel, or set `status.bindAddress` to `0.0.0.0` on a network you trust.                                                                                                                                                                                                                                                                                                                             |
| `421 Misdirected request`                                | On a loopback address it answers only `localhost`, `127.x.x.x` and `[::1]`, on any port, against DNS rebinding. Use one of those; an SSH tunnel works from any local port (`ssh -L 18080:127.0.0.1:8080 pi@gateway`, then `http://localhost:18080`). Bound to the network (`0.0.0.0`) it answers IP addresses, `localhost` and the machine's own host name (and `<name>.local`); to open it by another DNS name, add that name to `status.hostNames`. |
| Only the API, no page                                    | The page is not built. Run `pnpm --filter @ot-gateway/web build` and reinstall; the image always includes it.                                                                                                                                                                                                                                                                                                                                         |
| An old page in a checkout                                | The log says "the status page's build is older than its sources": `otg run` serves `apps/web/out` as it is. Run `pnpm --filter @ot-gateway/web build` (`pnpm gateway` does it) and reload.                                                                                                                                                                                                                                                            |
| Settings has no Edit button                              | The notice above the cards says why. A read-only mount (a `compose.yaml` from v0.12.0 or earlier): mount the folder ([operations.md](operations.md#from-a-composeyaml-that-mounts-the-config-file-v0120-and-earlier)). A folder user 1000 may not write: `ls -ln`, then hand it to that user. A page on `0.0.0.0`: set `OT_GATEWAY_EDIT_TOKEN` in `ot-gateway.env` and restart.                                                                       |
| `Not applied: …` after Save                              | The new config did not start (the outbox's file, the broker), so the gateway runs the previous one again and the file holds it again. The message names the cause; fix it and save again.                                                                                                                                                                                                                                                             |
| `The config file changed since this form opened`         | It was edited by hand or from another browser. Load it again: the page never overwrites a change it has not seen. A change by hand needs a restart to take effect.                                                                                                                                                                                                                                                                                    |
| `status page not served; the gateway runs on without it` | The port is taken. Readings are unaffected; pick another `status.port`.                                                                                                                                                                                                                                                                                                                                                                               |
| A device shows `late`                                    | No read arrived for three poll intervals (at least 15 s), though the gateway has not marked the device failing yet: a polling cycle is stuck. It turns into `cycle-timeout` when it passes its deadline. Check for a machine notice at the top of the status page and `host.eventLoopLagMs` and `host.cpuPercent` in `/api/status`, then the log for the device id.                                                                                   |

## The machine

| Symptom                                                                                                          | Cause and fix                                                                                                                                                                                                                                                                                                                                               |
| ---------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `host reports a power or thermal condition` with `under_voltage`                                                 | The power supply or its cable is too weak. Use the official supply; this is the most common cause of SD-card corruption, so fix it before anything else.                                                                                                                                                                                                    |
| `throttled`, `soft_temperature_limit` or `host is hot`                                                           | The Pi is too warm: a case with a heatsink or a fan, and space around it in the cabinet. On kernel 6.12 and later the gateway sees only `host is hot`; `vcgencmd get_throttled` shows throttling.                                                                                                                                                           |
| `event loop stalled`                                                                                             | Something blocked the gateway for a second or more. On a Pi: a slow SD card during a large outbox write, swapping (check memory), or another program hogging the CPU. Repeated stalls make devices time out.                                                                                                                                                |
| `wall clock stepped` more than once after boot                                                                   | The time source is unreliable: check NTP (`timedatectl`). Deadlines are not affected; timestamps are.                                                                                                                                                                                                                                                       |
| `the outbox's disk is nearly full`                                                                               | Free space, or move `buffer.path` to a larger disk. Until then an outage cannot be buffered.                                                                                                                                                                                                                                                                |
| On a Mac: `host 192.168.x.y unreachable` within milliseconds, from a BACnet or Modbus device, while ping answers | macOS Local Network privacy refuses LAN traffic from a terminal app it has not allowed, and from a tmux or screen server started before (it is no longer counted as that app). Allow the app under System Settings > Privacy & Security > Local Network; inside tmux, `tmux kill-server` and start it again from that app, or run the command outside tmux. |

[operations.md](operations.md#the-machine) explains each of these lines.

## Codes

Every code a command reports: in its `--json` failure (`code`), as a `doctor` finding, as a device's `reason` in `status`, `events` and the health topic, or as a command's result. `ot-gateway explain <code>` prints the same, with what to check per protocol for a device's failure class (`--json` for agents); `ot-gateway explain` lists them all. This table is `apps/gateway/src/Codes.ts`, printed by `ot-gateway explain --markdown`; a test keeps the two the same, so a new code is one row there and this table pasted again.

| `no-config`               | check, run, doctor, read, write, broker, watch, publish, discover, import, points allow-commands, points read-only, config get, config set, config unset, config remove, config undo | No config file at the path given (ot-gateway.json in this folder when none is named).                                                                                                                           | Run the command in the gateway's folder, or name its config. ## Still stuck

Run `/setup` in Claude Code against the same config: step 7 reads the status API and the logs and walks the symptoms above. Or open an issue with the device make and model, firmware version and, if you can, a packet capture (CONTRIBUTING.md, "Reporting device quirks"), and attach the file `ot-gateway support` writes in the gateway's folder: versions, the config, status, the last day's events and the log lines the gateway keeps, with secrets redacted. Read it first: device addresses and names stay in it.
